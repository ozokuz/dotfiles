# Configuration tooling fit

Research date: **2026-11-10**. All external citations below are official project/vendor sources accessed on that date; undated living documentation is identified by this access date, not an invented publication date. Documentation review only, without installs, host changes, credential access, or runtime validation. This is a recommendation, not an accepted ADR. It preserves ADRs 0001–0003 and the requirements in [configuration-design.md](../configuration-design.md).

## Recommendation

Use **Ansible as the single application engine**, with a small repository entry point, explicit selection data, a managed-file conflict guard, and SOPS + age. Run it from a Linux checkout when requested; no AWX, daemon, permanent controller server, or paid service is required. A control node is the process's execution host, not necessarily a dedicated machine. Ansible's CLI needs no database or daemon. [Ansible installation](https://docs.ansible.com/projects/ansible/latest/intro_installation.html)

This recommendation prioritizes the stated **programs plus user/system configuration** scope. Its material compromise is Windows autonomy: native PowerShell can bootstrap transport and guide enrollment, but **cannot run Ansible locally**. A Windows user must invoke a reachable authorized Linux checkout, or explicitly accept WSL/container execution and its support caveats. If fresh Windows must complete every operation entirely locally without either, prefer **chezmoi plus bounded PowerShell/Bash package and system adapters** instead. That is a different maintenance tradeoff, not a capability Ansible already has.

Do not start with Ansible plus chezmoi. Two engines would introduce two file representations, state models, previews, capture workflows, and ordering boundaries. Add chezmoi later only if its interactive dotfile workflow demonstrably saves more complexity than the extra boundary costs.

## Shortlist

| Approach | Established functionality reused | Work still owned by this repository | Assessment |
| --- | --- | --- | --- |
| Ansible + small glue | Remote execution, Linux/Windows modules, packages, privilege handling, templates, services, conditional tasks | Selection validation, conflict/capture policy, operation boundaries, applied-state records, notifications, protected-key retrieval | Best fit for full host scope, with Linux execution requirement |
| chezmoi + small glue | Native Windows/Linux binary, home-file rendering, change detection and merge/capture commands | Package reconciliation, privileged system changes, dependency ordering, remote orchestration, cleanup history, notifications | Better native Windows/local experience; adapters may cease to be small as system scope grows |
| Ansible + chezmoi | System modules plus mature home-file workflow | All cross-engine ordering, shared selection resolution, secret handling, failure reporting | Reasonable only with strict ownership: chezmoi exclusively owns user files, Ansible owns system state |
| Custom runner alone | Native package managers, Git, SOPS | File rendering, conflict detection, state tracking, transports, retries and most orchestration | Highest reinvention burden; reject for the full design |

The table is an architectural judgment based on the capabilities below. Free/open-source CLI tooling has no seven-host licensing requirement; individual application licenses and package availability remain separate concerns. Ansible is GPLv3+, chezmoi MIT, and SOPS MPL-2.0. [Ansible license](https://github.com/ansible/ansible/blob/devel/COPYING), [chezmoi license](https://www.chezmoi.io/license/), [SOPS license](https://getsops.io/docs/#license)

## Verified Ansible constraints

**Controller and local bootstrap.** Native Windows cannot be a control node. Installation documentation lists WSL, but the Windows guide explicitly says WSL is unsupported and should not be used for production systems. Distinguish “can run” from supported operation. Prefer an existing Linux host for execution rather than making WSL mandatory on every Windows desktop. Linux can use local playbooks; Windows `connection: local` does not turn POSIX execution into Windows module execution. [Windows control-node guidance](https://docs.ansible.com/projects/ansible/latest/os_guide/intro_windows.html#using-windows-as-the-control-node), [local playbooks](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_delegation.html#local-playbooks)

Bash bootstrap installs the chosen runtime and module prerequisites before normal local application. Most Linux modules need managed-node Python, though Ansible itself need not be installed remotely. As a concrete reviewed baseline, the official matrix lists core **2.21** with controller Python **3.12–3.14** and target Python **3.9–3.14**. Pin a maintained core patch release and collection versions at implementation time. Core 2.18 is already EOL in this matrix, so it is a historical SSH support floor, not a recommended pin. `raw` can bootstrap Python with fact gathering disabled, but has no check/diff support. [Support matrix](https://docs.ansible.com/projects/ansible/latest/reference_appendices/release_and_maintenance.html#ansible-core-support-matrix), [raw](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/raw_module.html)

**Windows transport.** Official SSH support began in **ansible-core 2.18**, after experimental availability since 2.8. It requires the **Windows-shipped OpenSSH**, at least **7.9.0.0**; upstream Win32-OpenSSH packages are expressly outside that support statement. The docs identify Server 2022 as the effective server baseline because Server 2019 ships 7.7.2.1. Do not translate this into “Windows desktops unsupported”: inspect each desktop's shipped version and OS lifecycle. Configure `ansible_connection=ssh` and shell type matching the target default shell, preferably PowerShell. Key authentication does not delegate credentials for access to a third machine. [Exact Windows SSH support](https://docs.ansible.com/projects/ansible/latest/os_guide/windows_ssh.html)

Microsoft documents OpenSSH as a feature on demand from Windows 10 build 1809, which establishes availability, not compliance with Ansible's minimum. PowerShell bootstrap must enable/authenticate the selected connection before remote application is possible. WSL remains its own Linux host, with its own reachability and prerequisites. [Microsoft OpenSSH overview, updated 2025-02-20](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-overview)

Do not reject Windows SSH categorically. Prefer it for a verified modern desktop in this non-domain fleet. For a host outside its support envelope, either explicitly update the supported OS component or select WinRM/PSRP. Both WinRM plugins require additional controller Python dependencies, a configured listener and authentication. WinRM has restrictions including noninteractive execution and Windows Update/DPAPI access; some installers require a different logon context or `become`. Neither transport is a desktop interactive session. [WinRM setup and limitations](https://docs.ansible.com/projects/ansible/latest/os_guide/windows_winrm.html)

**Module semantics.** SSH changes transport, not operating-system APIs: Linux Python modules do not generally work on Windows. Use the Windows collections and PowerShell modules for Windows targets. Collection pins and per-tool installation mappings remain necessary. [Windows modules](https://docs.ansible.com/projects/ansible/latest/os_guide/intro_windows.html#which-modules-are-available)

**Packages.** Reuse `apt`, `community.general.pacman`, and appropriate Windows modules rather than wrapping every package CLI. `apt` needs `python3-apt` and can automatically install module dependencies; bootstrap should make these changes explicit. Pacman's module warns against assuming AUR-helper compatibility. Chocolatey's module provides present/latest/absent operations, but availability of that module is not a reason to choose Chocolatey over WinGet for all Windows tools. WinGet availability depends on App Installer registration and the user context; verify remote/session behavior for the selected Windows installation method. [apt](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/apt_module.html), [pacman](https://docs.ansible.com/projects/ansible/latest/collections/community/general/pacman_module.html), [Chocolatey](https://docs.ansible.com/projects/ansible/latest/collections/chocolatey/chocolatey/win_chocolatey_module.html), [Microsoft WinGet](https://learn.microsoft.com/en-us/windows/package-manager/winget/)

**Preview and local edits.** Check mode only predicts supported module actions. Unsupported modules skip work, registered-result conditionals may lack useful results, and `check_mode: false` tasks can still execute normally. Diff support is also per module. A successful check cannot promise that dependencies, installer side effects, privileges or a real transaction will succeed. [Check and diff modes](https://docs.ansible.com/projects/ansible/latest/playbooks_checkmode.html)

Normal file convergence does not implement the required “keep local / capture / restore” choice. For example, `copy` normally replaces differing content; `force: false` only avoids replacing an existing file, without deciding whether it is an intentional edit. Backup is recovery assistance, not conflict detection. Add a reusable guard before **every** managed-file writer, including system files. [Copy semantics](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/copy_module.html)

## Verified chezmoi fit and limits

Chezmoi runs as a single binary on Windows and Linux. Its intended scope is the user's home directory; the project strongly discourages treating `/` or `C:\` as its destination for full system management. Arbitrary privileged scripts are possible, but their existence does not provide a system-management model. [Platform and scope](https://www.chezmoi.io/user-guide/frequently-asked-questions/design/#why-not-use-ansiblechefpuppetsalt-or-similar-to-manage-my-dotfiles-instead), [Windows elevation guidance](https://www.chezmoi.io/user-guide/machines/windows/)

`apply` prompts if a target has changed since chezmoi last wrote it; `merge` supports reconciling source, destination and computed target. This is closer to the desired capture workflow than plain Ansible templates. Retain prompts or fail closed unattended; avoid force application. Capturing a generated file still requires deciding which shared/platform/host input should change. [apply](https://www.chezmoi.io/reference/commands/apply/), [merge](https://www.chezmoi.io/reference/commands/merge/)

Its documented declarative-package pattern is data plus imperative scripts, not native package reconciliation. `run_once` and `run_onchange` remember successful script content, not whether the package is still installed. Scripts must remain idempotent. Dry-run skips scripts; verbose execution prints their contents, and diff normally includes pending scripts. Neither mode previews package-manager effects. Separate install/configure/upgrade/cleanup entry points would be repository code. [Package pattern](https://www.chezmoi.io/user-guide/advanced/install-packages-declaratively/), [script execution and disclosure](https://www.chezmoi.io/user-guide/use-scripts-to-perform-actions/)

Chezmoi's built-in age encryption is **not SOPS file-format support**. SOPS integration can use a configured generic secret command, through `secret` or JSON-parsing `secretJSON`, backed by a small SOPS helper. That does not automatically fetch the separate private repository or protect rendered plaintext in previews. [Age encryption](https://www.chezmoi.io/user-guide/encryption/age/), [secret](https://www.chezmoi.io/reference/templates/secret-functions/secret/), [secretJSON](https://www.chezmoi.io/reference/templates/secret-functions/secretJSON/)

Its `ssh` convenience command installs chezmoi and invokes `init --apply`. That immediate application is unsuitable as the fleet preview boundary, and its documented package-manager fallback does not establish native Windows remote bootstrap support. Use explicit transport to the same host-local entry point instead. [ssh command](https://www.chezmoi.io/reference/commands/ssh/)

## Secrets: separate distribution, decryption and protection

Keep the encrypted repository **outside the configuration source tree**, with an explicit URL and recorded immutable secrets revision. Authenticate Git separately from decryption. Fetch only ciphertext into its own checkout, then resolve approved secret references against that revision. Neither tool's local secret lookup performs GitHub enrollment or establishes revision coordination automatically. Ansible's `community.sops.sops` lookup reads a **controller-local** encrypted file and requires the `sops` executable there; it is an extra collection, not part of core. [SOPS lookup](https://docs.ansible.com/projects/ansible/latest/collections/community/sops/sops_lookup.html)

For the recommended remote path, decrypt on the authorized management host and deliver only required application values over the authenticated connection. Managed hosts need not all hold GitHub credentials or decrypt identities. Hosts needing independent local application must enroll their own access and appropriate decrypt capability. Offline ciphertext can be used only if its identity is available; a fresh host cannot recover an unavailable key from ciphertext.

SOPS looks for age `keys.txt` under Linux's user configuration directory or `%AppData%\sops\age` on Windows. It also accepts `SOPS_AGE_KEY_FILE`, `SOPS_AGE_KEY`, or **`SOPS_AGE_KEY_CMD`**. These are key input mechanisms, not OS-keychain enrollment. Prefer a command retrieving an enrolled identity from protected storage over keeping a raw private identity in the default file. The Ansible lookup exposes `age_key_cmd` since community.sops **2.3.0**, requiring SOPS **3.10.0+**. [SOPS age identities](https://raw.githubusercontent.com/getsops/docs/main/content/en/docs/usage/identities/age/_index.md), [lookup version requirements](https://docs.ansible.com/projects/ansible/latest/collections/community/sops/sops_lookup.html)

Human enrollment must authorize repository access and securely provision or generate the chosen identity, then add its public recipient to the appropriate encrypted files. A single shared age identity is simplest but grants access to every file addressed to it. Separate recipient sets limit decrypt scope at **file** granularity; selecting one JSON key is not access isolation. Do not adopt per-host identities by implication. Start with an explicitly agreed recipient grouping and separately retained recovery recipient/backup.

For Git access, use existing attended authentication with a protected credential helper; read-only deploy keys are an alternative for independent retrieval, scoped to one repository but still requiring private-key protection. A deploy key grants repository access, not age decryption. GCM defaults to Windows Credential Manager on Windows, has no Linux default, and documents that its Windows Credential Manager store does not work over SSH/network sessions. Its Linux Secret Service store needs the provider and session bus. Do not assume remote Windows tasks can reuse interactive enrollment. [GitHub deploy keys](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys), [GCM stores and session limitations](https://github.com/git-ecosystem/git-credential-manager/blob/main/docs/credstores.md)

Use a small protected-key retrieval boundary: Windows Credential Manager or user DPAPI in a validated logon context; Linux Secret Service on desktops; an explicitly configured system service with `LoadCredentialEncrypted=` where supported on headless hosts. WSL needs an explicit Windows bridge or its own protected store. These are proposed adapters, not automatic SOPS features. Multiple desktop sessions should share the chosen user Secret Service rather than duplicate identities per compositor. Locked/unreachable stores block dependent work without plaintext fallback. [CredRead logon context](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw), [Secret Service](https://specifications.freedesktop.org/secret-service/latest/ch01.html), [systemd credentials](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html#Credentials)

Keep secret values out of task names, command arguments, preview rendering and script text. For Ansible use `no_log: true` plus `diff: false` on secret-bearing operations; disable debug output and avoid secret fact caches. The reviewed 2.20 logging docs warn that `no_log` does not protect debugging output. Do not base the design on newer/development masking claims without pinning and verifying that release. For either engine, preview secret references only and apply secret files in a separate protected phase. Key commands must emit identities only into the intended private pipe; suppress their stderr details and shell tracing. [Ansible logging safeguards](https://docs.ansible.com/projects/ansible-core/2.20/reference_appendices/logging.html)

## Minimal repository architecture and visible compromises

The following is proposed repository behavior, **not a claim of native tool features**:

1. **Resolve before mutation.** One explicit host definition selects tools/configuration and optional nonnested bundles. Expand bundles as sets, validate platform support and contradictory selections, then resolve shared → platform → host values. Use native includes or complete rendered files rather than universal deep merging. Desktop sessions can coexist; choose defaults and genuinely exclusive resources explicitly. Rebuild package selections from scratch.
2. **Keep operations distinct.** `preview`, installation of missing tools, configuration application, upgrades, capture, and cleanup have separate entry points. Configuration-only selections skip installation. An explicit managed-item record distinguishes formerly requested items from unrelated installed programs. Deselection only creates cleanup candidates. No blanket autoremove or unselected-file deletion.
3. **Guard file changes.** Record the last successfully applied fingerprint per managed nonsecret file. Before writing, compare actual/last-applied/desired content and metadata. First adoption of an existing differing file is a conflict too. Preserve and block conflicting paths until a keep-local exception, reviewed capture into the chosen layer, or explicit restore is selected. Recheck immediately before mutation, back up replacements, and keep application-owned state outside management. Secret conflicts reveal references only, with protected comparison material rather than a public plaintext baseline.
4. **Run one engine.** Linux local application uses local Ansible; remote application runs pinned playbooks from an authorized Linux checkout with named hosts and an immutable configuration revision. PowerShell bootstrap enrolls Windows transport and points at that execution path. A PowerShell-only fresh host without reachable Linux execution stops after enrollment; installing WSL can require extra setup or reboot and is an explicit alternative. No permanent fleet controller is needed.
5. **Resume honestly.** Record successful per-item progress rather than marking the whole host current after partial failure. Gate dependent configuration on prerequisite success; continue independent work deliberately. Retry idempotent operations, not an automatic rollback of installers or arbitrary system changes.
6. **Keep auxiliary work small.** Host-local login/periodic checks compare a digest of resolved relevant inputs and pinned skill revisions with successfully applied state. Notify without applying, deduplicated by intended digest. Third-party skills are vendored or fetched at exact commits into staging, validated for agent compatibility, then deployed through the managed-file path. Ansible Git can pin revisions on the controller; Windows receives staged files through Windows modules rather than an assumed POSIX Git task. [Git module](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/git_module.html)

The file guard/capture layer is the main custom component Ansible does not remove. Bound it to repository-owned files; do not build a general configuration language. Check/diff is useful supporting evidence, while explicit validation and honest “unknown until apply” results cover operations that cannot be simulated.

**Package separation has a real limit.** Arch supports full system upgrades, not refreshing repositories and selectively upgrading a subset. Missing-package installation can also require dependency changes. If installation cannot proceed safely against the current synchronized state, stop and report that an explicit upgrade operation is needed; never silently run `pacman -Sy` or upgrade the system to satisfy setup. This affects every shortlist option. “No requested upgrades” cannot promise that a package transaction never changes an installed dependency. [Arch maintenance policy](https://wiki.archlinux.org/title/System_maintenance#Partial_upgrades_are_unsupported)

## Remaining decisions

- Accept Linux execution for Windows management, or require fully local native Windows operation and choose the chezmoi/adapters alternative. This is the architecture decision with the greatest effect on complexity.
- Inventory actual Windows OS/OpenSSH versions and choose SSH or PSRP per supported host; validate user-scope installers, elevation and secret-store access in the real session type.
- Select Windows package defaults, explicit exceptions and any AUR support. Decide how the preview describes dependency upgrades and blocked Arch installs.
- Choose recipient grouping, controller-side versus host-side decryption, Git credential mechanisms, secrets revision coordination, and independently usable recovery material. No per-host identity scheme is assumed accepted.
- Define the exact managed-file adoption/keep-local contract and scope of capture. Validate that narrow contract before implementing a broad tool catalog.

No host migration, old configuration removal, or live symlink-target edit is implied by this recommendation.
